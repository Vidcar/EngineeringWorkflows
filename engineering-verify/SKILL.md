# Engineering Verify

Own a request to execute defined checks or create or maintain verification assets. For a mixed implementation request, engineering-workflows owns the final outcome; an existing owner retains it. A support assignment inherits its owner, scope, allowed writes, review depth, and budget. Return evidence without starting another lifecycle or invoking other engineering skills.

Resolve `engineering-workflows` by exact catalog name and read its `references/contract.md` once per task; reading is not invocation. If unavailable, continue safe useful verification and report the precise limitation. Preserve user work, scope, and authority.

Identify each claimed behavior, the actual artifact including dirty or new bytes, environment, entrypoint, and authorized effects. Derive expected outcomes from the requirement or an independent oracle. Choose checks that fail for the relevant defect and survive harmless internal changes. For a repair, reproduce the original failure or a failing regression check when practical; report when this was unavailable. Do not weaken an assertion to make it pass or derive expected values from the code under test.

Exercise the real path and consequential persisted or external effects when warranted, using safe boundaries and only authorized operations. Confirm the running version and data; compilation, mocked behavior, screenshots, or a model prove only their specific claims. Recheck the integrated result after material changes. Report input, observation, result and limits, separating failures, blocked checks, and untested claims. Use [methods.md](references/methods.md) for application, visual, formal, and verification-asset work.
