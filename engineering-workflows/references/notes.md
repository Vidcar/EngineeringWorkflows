# Writing and reusable lessons

For substantial technical prose, lead with the outcome and explain the consequence
before implementation detail. Preserve exact claims, evidence, uncertainty and
useful rationale. Remove filler and repeated narration; do not strengthen an
unverified claim while shortening it. An editorial request stays within its text.
Code cleanup remains the implementation owner's job.

Capture a lesson only when evidence shows a reusable failure or discovery. Prefer
the smallest existing mechanism that prevents recurrence: ownership, a boundary
check, a test, a helper or a concise instruction with a concrete example. Verify
that it catches the failure and permits a legitimate case. Do not generalise a
single preference into universal policy, or edit unrelated skills/settings.
Store the lesson once with its scope and evidence; avoid a permanent log of routine
activity. A retrospective-only request returns findings and a concrete proposal.
