# Write clearly and keep useful lessons

## Explain the result

Lead technical prose with the result and why it matters. Preserve exact claims,
evidence, uncertainty and useful rationale. Cut filler and repeated narration
without making an unverified claim sound stronger. An editing request stays
within the requested text; code cleanup belongs to the implementation task.

Explain mechanisms from the code and motivation from the available record; label
inference and missing history. For procedures, use real commands and paths, state
the expected observation, and check executable steps when practical. Use visuals
when they clarify a relationship or a visible change, based on actual evidence.

For a status or handoff, establish current outcomes and remaining work. List only
decisions the user must make, with the recommendation, relevant evidence and
tradeoff. Work the agent can finish is not a user action item.

## Keep consequential decisions

Use the existing task record when later review or resumption needs it. Record the
choice, reason, evidence and result for significant pivots, rejected approaches
or changed acceptance conditions. Check that evidence pointers resolve to the
claimed result. Correct a mistaken claim explicitly rather than hiding the failed
attempt. A log entry does not replace a check, and routine actions need no log.

## Prevent repeated mistakes

Capture a lesson when evidence shows a reusable failure or discovery. For a
recurring correction, inspect actual examples and choose the smallest effective
prevention. Prefer clear ownership or an impossible-to-misuse interface, then
types, boundary validation, actionable checks or tests. Use a short instruction
with a concrete example when the remaining decision needs judgment.

Exercise the prevention through the real check path against a representative
past mistake and a legitimate case. Preserve comments that explain external
constraints, compatibility or non-obvious rationale until equivalent enforcement
or evidence makes them redundant. An unenforced constraint is not evidence that
the constraint can be discarded.

Keep the lesson once, with its scope and evidence. A single preference is not a
universal rule. Avoid permanent logs of routine activity or changes to unrelated
skills and settings. A retrospective-only request ends with findings and a
concrete proposal. When the user requests pack changes, use Configure to adjust
the relevant skill or trigger and evaluate the behaviour; ordinary lessons do
not authorize changes to installed skills.
